# Future Hero Quest · 内容方向 Roadmap

更新时间：2026-05-02 11:55 UTC+8

本文档回答“这个项目以后往哪里走”。

## 核心定位

Future Hero Quest 的长期方向不是单纯“多做几关”，而是把一个时空协作原型打磨成短篇双人解谜作品：

- 两名玩家永远分处不同时代。
- 每人只能看到自己时代的事实。
- 解谜靠沟通、验证、反馈，而不是一个人收集全部信息。
- 过去可以改变未来，未来可以把线索反馈给过去。
- 技术上优先同步“语义事件”，不追求全物理状态同步。

## 版本定义

| 版本 | 定义 | 目标 | 是否属于当前 DDL |
|---|---|---|---|
| v1.0 · Hackathon Submission Cut | 黑客松提交版 | 可下载、可运行、双人可验收、页面可信 | 是 |

## v1.0 内容边界

v1.0 只需要证明核心概念成立：

| 模块 | v1.0 标准 |
|---|---|
| 联网 | 两个客户端能创建 / 加入同一 Photon 房间 |
| 关卡 | `Bridge` / `Archive` / `ClubRoom` 三关可连续验收 |
| 时空关系 | 过去操作能改变未来状态，未来能反馈信息 |
| 结尾 | 有最小完成点，不要求完整叙事收束 |
| 平台 | Windows 优先 |
| 页面 | GitHub / itch.io 说明准确，不承诺未实现内容 |

v1.0 不负责：

- 完整剧情章节。
- WebGL / Mac 稳定发布。
- 房间名、匹配、断线恢复等完整联机体验。
- 统一美术风格和完整动画。
- 旧版 Tree / Switch / Box 关卡设计全部回收。

## v1.1 体验修正方向

目标：让第一次玩的两名玩家更少迷路。

| 方向 | 可能内容 |
|---|---|
| 目标提示 | 每关当前目标、下一步提示、角色侧提示差异 |
| 交互反馈 | 可交互物高亮、成功/失败反馈、错误状态说明 |
| 失败恢复 | Reset 语义更清楚，避免玩家不知道是否卡死 |
| 房间流程 | 房间名、创建/加入状态、等待第二名玩家提示 |
| 验收脚本 | 固化一份 5-10 分钟试玩流程 |

## v1.5 短篇作品方向

目标：让它从技术 demo 变成一个完整短篇。

| 方向 | 可能内容 |
|---|---|
| 开场 | 用 30 秒解释 1996 / 2026 的关系 |
| 角色 | K / M 的身份、动机、称呼和对话风格 |
| 章节结构 | 三关之间有轻量过渡，而不是纯场景跳转 |
| 结尾 | 完成最后门锁后有一段收束反馈 |
| UI 风格 | 标题、按钮、提示、对话统一视觉语言 |
| 音频 | 关键状态变化有稳定 SFX / BGM 层次 |

## v2.0 扩展 Demo 方向

目标：增加机制深度和可展示长度。

| 方向 | 可能内容 |
|---|---|
| 关卡扩展 | 回收旧版 Tree / Switch / Box 概念，改造成新时间线规则 |
| 双向机制 | 未来向过去传递线索或物件状态，而不破坏单一时间线 |
| 平台扩展 | WebGL / Mac 构建验证 |
| 联网增强 | 房间名、角色选择、重连、ready 状态 |
| 视觉统一 | 固定 low-poly + 2D/2.5D 表现规范 |
| 关卡工具 | 用 ScriptableObject / prefab 约束减少场景 YAML 冲突 |

## v3.0 正式项目方向

目标：判断 Future Hero Quest 是否值得继续做成正式项目。

| 方向 | 需要验证的问题 |
|---|---|
| 核心乐趣 | 玩家是否真的享受“信息差 + 沟通 + 时间线反馈” |
| 内容生产 | 每个关卡是否能用稳定模板生产，而不是每次手写 |
| 联网成本 | Photon / 服务器 / 房间管理是否能支持公开试玩 |
| 美术成本 | 2.5D 方案是否能长期保持一致性 |
| 叙事空间 | 1996 / 2026 是否能支撑多章节故事 |

## 内容支柱

| 支柱 | 说明 |
|---|---|
| 信息差 | 两个玩家看到不同事实，必须交流 |
| 可验证反馈 | 玩家操作要快速看到“未来变了”或“过去收到线索” |
| 轻量规则 | 每关只引入一个主要机制，不堆系统 |
| 双人尊重 | 两边都要有有效行动，不让一方只当观众 |
| 可发布诚实 | 页面和版本号只承诺实际可玩的内容 |

## 不做清单

- DDL 前不重做三关。
- DDL 前不引入新联网框架。
- DDL 前不把 WebGL/Mac 作为阻塞项。
- DDL 前不追完整剧情演出。
- DDL 前不做大规模资源目录重排。
- DDL 前不把 v1.1/v2.0 backlog 当作 v1.0 必须完成项。
